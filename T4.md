# ЧАСТЬ 1. ТЕСТ-ПЛАН

## 1. Идентификатор плана
| Поле | Значение |
|:---|:---|
| **ID** | `TP-INT-SERVICE-AB-001` |
| **Версия** | `1.0` |

## 2. Введение
**Цели:** Обеспечить проверку интеграционного взаимодействия между Сервисом А и Сервисом В через брокер сообщений RabbitMQ, включая асинхронную обработку запросов, упорядочивание команд и управление статусами услуг.  
**Область применения:** Документ используется командой QA для тестирования микросервисной архитектуры с асинхронным взаимодействием.  

## 3. Объекты тестирования
| Компонент | Описание |
|:---|:---|
| **Сервис А** | Прием REST-запросов, асинхронная отправка/прием AMQP-сообщений, управление статусом услуги, контроль очередности отправки команд |
| **Сервис В** | Обработка AMQP-сообщений, выполнение бизнес-логики (подключение/отключение/блокировка услуги), отправка ответных AMQP-сообщений с результатами |
| **RabbitMQ** | Брокер сообщений для маршрутизации и хранения сообщений между микросервисами |

## 4. Особенности, подлежащие тестированию
1. REST API Сервиса А (подключение/отключение/блокировка услуги)
2. Асинхронная отправка AMQP-сообщений от Сервиса А к Сервису В
3. Упорядочивание команд (отправка следующей команды только после ответа на предыдущую)
4. Изменение статуса услуги только после положительного AMQP-ответа от Сервиса В
5. Независимость приема REST-запросов от обработки предыдущих запросов
6. Обработка ошибок и сбоев инфраструктуры (недоступность RabbitMQ, Сервиса В)

## 5. Особенности, не подлежащие тестированию
1. **Нагрузочное тестирование:** Вынесено в отдельный план `TP-PERF-003`
2. **Внутренняя бизнес-логика Сервиса В:** Тестируется только корректность ответов
3. **UI/UX:** Веб-интерфейс не тестируется в рамках этого плана

## 6. Подход
- **Типы тестирования:** Интеграционное, Функциональное, Асинхронное, Негативное
- **Уровень:** Integration Testing
- **Инструменты:** Postman (REST), RabbitMQ Management Plugin (AMQP), Docker (окружение), Python scripts (эмуляция сбоев)
- **Данные:** Тестовые услуги создаются скриптом `seed_services.py`
- **Автоматизация:** Критические сценарии (очередность, асинхронность) покрываются автотестами

## 7. Критерии приёмки
**Входные критерии (Entry Criteria):**
- Развернуты все компоненты (Сервис А, Сервис В, RabbitMQ) в тестовом окружении
- Настроены очереди и exchange в RabbitMQ
- Доступны логи всех компонентов

**Выходные критерии (Exit Criteria):**
- 100% тестов с приоритетом **Blocker** и **Critical** пройдены
- Подтверждено упорядочивание команд (не отправляется следующая команда без ответа на предыдущую)
- Статус услуги изменяется только после положительного AMQP-ответа
- Не осталось багов с приоритетом **Critical** и **High**

## 8. Критерии приостановки/возобновления
**Приостановка (Stop Testing):**
- Недоступность RabbitMQ или критические ошибки брокера
- Сервис А падает при приеме REST-запросов
- Потеря сообщений в очереди без возможности восстановления

**Возобновление (Resume Testing):**
- Все компоненты восстановлены и доступны
- Подтверждена доставка тестового сообщения через всю цепочку
- Получено подтверждение от команды разработки о готовности

## 9. Результаты тестирования
**Деливерабли:**
- Отчет о тестировании (Test Summary Report)
- Логи AMQP-сообщений (отправка/получение)
- Заведенные баг-репорты в Jira
- Диаграмма последовательности для негативных сценариев

- **Окружение:** Docker Compose (локальное), Stage Environment
- **Софт:** Postman, RabbitMQ Management UI, Wireshark (опционально для AMQP), Jira
